# NumberInbox light-mode branding finish — implementation and TDD plan

Status: implemented on 2026-10-11; kept as the record of the agreed approach and its TDD
sequence. Scope was the light mobile UI and the mobile-web app banner; the document itself
changed no app code.

Post-implementation corrections worth keeping in mind:

- The app-wide light `SystemUiOverlayStyle` region wraps every route, so the navy `HomeView`
  splash publishes its own nested region for white icons rather than relying on an imperative
  `SystemChrome` call, which the app-wide region would otherwise override on the next frame.
- The mobile Compose action branches on `Theme.of(context).brightness`: green in light mode,
  the prior blue in dark mode.

## Outcome

The phone-number and OTP phases of the welcome screen should feel like one flow: **Send code** and **Verify** use the same NumberInbox gradient, 54 logical-pixel minimum height, 14-pixel corner radius, label treatment, loading treatment, and full available width. The mobile **Compose** floating action keeps its pill shape, 154 × 60 logical-pixel expanded size, scroll animation, icon, position, and behavior, but uses the NumberInbox primary action green instead of blue. The desktop/sidebar Compose button is already green in light mode and should remain so.

The mobile-web smart banner must open the installed NumberInbox app or lead to the correct NumberInbox store listing, never Twake Mail. Its visible colors and copy should match the light brand. White native app bars must use readable dark system status-bar icons. Do not change authentication, mail behavior, routes, package IDs, internal class/file names, or the dark-theme design. Banner copy and the existing web deep-link value are the only text/routing values in scope.

Use the established contrast-safe action colors `NumberInboxPalette.actionGreen` (`#047857`) and `NumberInboxPalette.actionBlue` (`#0369A1`) for the login gradient. These are deliberately darker than the logo's emerald/cyan (`#10B981`/`#06B6D4`) so white control text remains legible. Use `AppColor.colorComposeButton` (`#047857`) for light-mode mobile Compose, matching the existing light sidebar Compose control. Keep the blue color for the current dark-mode floating button until the later dark-mode phase, or verify an existing dark-mode requirement before changing it.

## Root cause and exact edit surface

- In `lib/features/starting_page/presentation/twake_welcome/twake_welcome_view.dart`, `_buildSendCodeButton` at approximately line 174 wraps a transparent `FilledButton` in a green-to-blue `DecoratedBox` and sets `minimumSize: Size.fromHeight(54)`. `_buildVerifyButton` at approximately line 222 constructs an ordinary `FilledButton` without the gradient or height. `ThemeUtils.buildAppTheme()` supplies solid `actionGreen` to ordinary `FilledButton`s, so the OTP phase is shorter and solid green. The gradient was added in the rebrand while the Verify path retained its prior structure.
- In `lib/features/base/widget/compose_floating_button.dart`, `ScrollingFloatingButtonAnimated` receives `color: AppColor.blue700` (`#0369A1`) at approximately line 50. This shared widget is used by `thread_view.dart` and `sending_queue_view.dart`, so one focused change covers the mobile Inbox and Sending Queue Compose actions. The blue assignment predates the NumberInbox rebrand.
- `lib/features/mailbox_dashboard/presentation/widgets/compose_button_widget.dart` already uses `AppColor.colorComposeButton` in light mode for the desktop/sidebar primary action. Do not inadvertently alter its size, padding, dark-mode behavior, or tests.
- The app's light-theme `FilledButtonTheme` is in `core/lib/presentation/utils/theme_utils.dart`. It should remain solid green for ordinary buttons; a global gradient or global 54-pixel size would change unrelated controls. Put the gradient treatment in a small reusable welcome-flow button/widget instead.
- `web/worker_service/worker_service.js` still sends iOS users to `https://apps.apple.com/app/twake-mail/id1587086189` and tries `twakemail.mobile://openapp`. The installed apps register `numberinbox.mobile` in `ios/Runner/Info.plist` and `android/app/src/main/AndroidManifest.xml`; Android declares the host as `openApp`. The banner therefore attempts the wrong app scheme and can fall back to the upstream App Store listing. Do not guess a NumberInbox App Store ID: verify an owned listing URL before enabling that fallback.
- `web/worker_service/style.css` still uses a pink/blue-tinted `#FFFBFE` banner background. `web/i18n/{en,fr,de,vi}.json` and `web/i18n/translater.js` use generic convenience copy. The actual image in `web/worker_service/img/tmail-*.png` is already the NumberInbox mark despite its internal filename; no logo replacement is required. The banner's visible text is initially populated on `DOMContentLoaded` while translations load asynchronously, so localized copy can remain on the English fallback unless the loaded language is applied again.
- `core/lib/presentation/utils/theme_utils.dart` sets a white shared `AppBarTheme` with `SystemUiOverlayStyle.light`, which requests light Android status-bar icons. Material `AppBar` screens such as `lib/features/numberinbox/about_numberinbox.dart` and `account_deletion_page.dart` inherit that contrast mismatch. The dark navy Flutter startup and white login screens use their own `ThemeUtils` system UI calls and must remain correct.

## Implementation sequence

1. Add a focused, reusable button for the two welcome phases, preferably beside `twake_welcome_view.dart` or in a local `widgets/` file. Its inputs are a stable key, label, `VoidCallback? onPressed`, and `bool isLoading`. One implementation owns the full-width constraint, 54-pixel minimum height, 14-pixel radius, gradient, text style, and progress indicator. Preserve existing keys `otp_send_cta` and `otp_verify_cta` on the actual tappable buttons so current tests and accessibility finders still work. Keep Material button semantics, keyboard focus, tap feedback, and a clipped/radius-matched ripple; do not place an opaque Material surface over the gradient.
2. Use that button from `_buildSendCodeButton` and `_buildVerifyButton`. Pass the existing `sendCode()`/`verifyCode()` callbacks and `sending`/`verifying` states unchanged. While loading, show a **white, visible 20 × 20 progress indicator** on the branded background and suppress additional taps. If the widget is ever disabled for a non-loading reason, show a visibly disabled neutral fill rather than leaving a fully saturated gradient behind an inactive button. Keep label contrast, semantics, and focus styling intact. Avoid a gradient drawn outside a transparent disabled button without accounting for its state.
3. In `compose_floating_button.dart`, resolve the floating button color from the light brand action token (ideally `AppColor.colorComposeButton`) while retaining its current dark-mode color. Do not modify `ScrollingFloatingButtonAnimated`, its `154 × 60` expanded geometry, circular collapsed geometry, `scrollController`, `onTap`, icon, animation, or route callers. Avoid hardcoding a second green literal.
4. Confirm the SVG compose icon is still white against the green fill and that the existing sidebar Compose control is unaffected. Do not rebrand every blue secondary action; this plan concerns the prominent primary CTAs called out in the review.
5. Correct the web banner's launch destination. Use `numberinbox.mobile://openApp`, matching the Android manifest host exactly, then verify the iOS URL handler and Dart `DeepLinksManager` accept it. Do not broaden the app's URL handlers or change bundle IDs. Replace the Twake iOS fallback with the verified NumberInbox App Store URL once it exists. If that listing is not live, suppress the iOS banner or its store fallback rather than sending users to an unrelated listing; apply the same rule to Android if its Play listing is not live. Keep the existing blur/visibility cancellation behavior, and test installed-app and missing-app cases on devices. The no-token banner link only needs to foreground the app and land in its normal signed-in or sign-in state; it must not bypass authentication.
6. Restyle the web banner in `web/worker_service/style.css` with the existing light palette: ice `#F5F7EB` or white surface, navy `#0F172A` text, cool-gray `#E5E7EB` border, and contrast-safe action green `#047857` for Open. Use the established tagline “Email, reimagined with your number.” in the English banner source and fallback. Translate that meaning in `fr`, `de`, and `vi` instead of silently replacing those locales with English. Apply translations after the fetch resolves, retaining English when the locale file is unavailable. Keep the existing NumberInbox mark and banner close behavior. Make Open a keyboard-focusable control if the markup is touched, without changing its visual size or click handler.
7. Change the shared white `AppBarTheme.systemOverlayStyle` to dark status-bar icons, preferably `SystemUiOverlayStyle.dark` or an explicit equivalent. Do not invert the navy splash or white login overlays. Check whether any page intentionally paints a dark background under a Material `AppBar`; give such a page a local overlay override instead of weakening the white-bar default.

## TDD: red → green → refactor

Write the assertions **before** changing production widgets, run the focused test, and retain the expected initial failure in the agent's report. Then implement the minimum change, rerun, and refactor to the shared welcome button. Test visual contract and behavior independently so a screenshot comparison is not the only evidence.

1. Extend `test/features/starting_page/twake_welcome_view_test.dart` using its existing `ThemeUtils.buildAppTheme()` harness. In the code phase, set `OtpPhase.code` through the existing controller setup or the stubbed `/v1/otp/start` transition and inspect `otp_verify_cta`. Assert both have the same two gradient stops in order, effective width, 54-pixel minimum rendered height, 14-pixel radius, white enabled label, and no overflow. The Verify comparison must fail against the current code.

If testing a genuinely disabled non-loading state through the new widget, assert a neutral disabled fill and disabled semantics. Do not rely on a `find.text` assertion alone: that would miss the styling defect.
3. Add `test/features/base/widget/compose_floating_button_test.dart` or a nearby focused test.
