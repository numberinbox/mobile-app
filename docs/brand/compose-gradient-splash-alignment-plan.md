# NumberInbox Compose gradient and splash alignment — TDD plan

## Goal and current behavior

Use the same contrast-safe green-to-blue gradient on every light-mode primary Compose action as on Send code, Verify, and Delete account. Keep Compose geometry and behavior intact. On startup, the native splash should show the N/@ mark alone, followed by the Flutter loading screen with the *same mark in the same apparent position and size* plus the wordmark and spinner below it. Both stages remain white; this work does not add an animation or change startup timing.

The shared `NumberInboxPalette` defines `actionGreen` (`#047857`) and `actionBlue` (`#0369A1`), but not a gradient token. `BrandedActionButton` assembles the gradient locally; the mobile floating Compose action and desktop sidebar Compose action use the solid `AppColor.colorComposeButton` (`#047857`). `ScrollingFloatingButtonAnimated` accepts only a `Color`. `HomeView` already centers its 120 dp image independently of the wordmark/spinner; its current widget test proves only Flutter-internal centering, not alignment with the preceding native frame. The native and Flutter assets have approximately 100 dp visible marks by design, so measure the live transition before changing padding or scale.

## Slice 1 — A single light-mode gradient

1. **Red:** Add a focused palette test asserting that a new `NumberInboxPalette.primaryActionGradient` goes left-to-right from `actionGreen` to `actionBlue`. Update welcome and deletion button tests to assert that their enabled and loading states paint this same token and that the disabled state remains neutral. These should fail before implementation.
2. **Green:** Define a `static const LinearGradient` in `core/lib/presentation/resources/numberinbox_palette.dart` and replace the inline enabled gradient in `BrandedActionButton` with it. Keep its existing 54 dp height, 14 dp radius, white text/spinner, disabled fill, semantics, and tap suppression. Do not replace `ColorScheme.primary` with a gradient: Flutter's theme color slots require colors.
3. Keep `AppColor.colorComposeButton` as the solid-color compatibility mapping for other existing consumers; if its declaration is touched, map it to `NumberInboxPalette.actionGreen` instead of repeating the hex literal. Do not globally turn ordinary green buttons into gradient buttons.

## Slice 2 — Mobile and web/desktop Compose

1. **Red, mobile:** Change `test/features/base/widget/compose_floating_button_test.dart` to expect the shared gradient in light mode, including after scroll collapse. Assert the 154 × 60 dp expanded geometry, pill radius, white label/icon, exactly one callback per tap, and the existing blue dark-mode fill. Add a focused test for `ScrollingFloatingButtonAnimated` showing that old color-only callers still paint their solid color.
2. **Green, mobile:** Add optional `Gradient? gradient` to `ScrollingFloatingButtonAnimated`. In its rounded `Ink` decoration, set `gradient` when provided and set `color` only when it is absent; this avoids a `BoxDecoration` with both fields. Retain its default `color`, Material/Ink ripple, scroll listener, animation, and public constructor behavior. Pass `NumberInboxPalette.primaryActionGradient` from `ComposeFloatingButton` only in light mode; keep `AppColor.blue700` in dark mode. Reuse the same gradient for expanded and collapsed states.
3. **Red, desktop:** Update `test/features/mailbox_dashboard/presentation/widgets/compose_button_widget_test.dart` to expect a visible gradient behind the light-mode sidebar button and a transparent `FilledButton` surface. Keep assertions for the existing key, white icon/text, 40 dp button height, resolved width, padding, one callback, and unchanged dark-mode design-system style. Add a focus/hover assertion so the gradient is not covered by an opaque state background.
4. **Green, desktop:** In `ComposeButtonWidget`, keep `LinagoraSidebarPrimaryAction` and its keyed `FilledButton`; do not fork `linagora_design_flutter`. For light mode, put the existing outer padding and alignment *outside* a stadium-shaped `DecoratedBox` carrying the shared gradient. Give the button a transparent background for normal, hovered, focused, pressed, and disabled states, with a visible but translucent state overlay and white foreground. Keep its current resolved width, 40 dp height, icon size/spacing, accessibility semantics, and keyboard activation. The gradient should cover only the interactive pill, not the padding around it. Dark mode continues through the existing design-system style without a gradient.

## Slice 3 — Measure and align the native-to-Flutter splash handoff

1. **Capture the failing behavior first.** On a reproducible Android emulator/device and iOS simulator/device, record a cold start at the highest practical frame rate. Save the last frame with only the native N/@ mark and the first frame with the Flutter wordmark/spinner. For each frame, record the screenshot size, device pixel ratio, status/navigation safe-area insets, and the visible mark's center and bounding width. Compare in logical pixels; target a center shift of at most 2 dp and no perceptible scale change. Keep the captures as QA evidence, excluding personal data.
2. **Red, geometry:** Extend `test/features/home/presentation/home_view_test.dart` so the mark's center is tested under at least two viewport sizes and unequal top/bottom insets. The position must stay fixed as wordmark/spinner content appears and must match a single native-splash anchor. Add a pure geometry unit test if an inset calculation is needed. Extend `test/branding/splash_config_test.dart` to compare visible alpha bounds and intended displayed size of the Flutter mark, iOS LaunchImage, regular Android image, and Android 12 image; retain centered padding and Android 12 safe-circle checks.
3. **Green, alignment:** Use the measured native center to place the Flutter N/@ mark in the same coordinate space, deriving any correction from viewport/system insets rather than an unexplained fixed offset. Derive the wordmark/spinner position from that same mark anchor so adding them cannot move it. If captures show only a size difference, correct the source or rendered size instead of adding a position offset. Keep native splash assets mark-only and leave platform-controlled launch behavior intact. Regenerate native resources only if their source artwork or configuration actually changes, using the repository's existing generator workflow; do not regenerate the hand-authored web splash.
4. Re-capture cold starts after the fix on Android 12+, an older Android version if supported, and iOS. Repeat with light and dark system appearances, a phone with unequal system insets, and large text. Check the first native frame, handoff, Flutter loading state, and transition to login/mailbox. The N/@ must not visibly jump, shrink, or clip; the wordmark and spinner remain below it, and the background stays white throughout.
